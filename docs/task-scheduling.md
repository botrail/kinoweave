# Task alternatives and schedule search

`SchedulePlanner` chooses robot assignments, concrete skill parameters and
resource orderings from a finite task catalog. It tries each generated
skeleton with the [multi-arm planner](multi-arm-manipulation.md), optionally
refines feasible plans, and keeps the best independently CPU-verified result.
Robot geometry and base PRMs are shared across attempts. This API runs
independently of Botrail, MuJoCo, Isaac Sim, or any simulator.

## Run the standalone demo

From an installed source checkout:

```bash
python examples/task_scheduling.py --output /tmp/task-run
```

Two synthetic Cartesian tools inspect two locations. Each task can be assigned
to either arm. One configured approach intersects a pillar and fails geometric
planning; another succeeds. The search first finds a serial schedule, then a
shorter parallel schedule by changing assignment. The traces are explicit
kinematic proxies, without physical inspection or controller semantics.

The output directory contains `domain.json`, the selected `problem.json`, its
verified `result.json`, and `schedule.json` with attempts, selected alternatives,
cost history, configuration, backend, cache statistics, and termination reason.
Always keep the selected problem/result together: a different skeleton has a
different input identity. The report also records the original candidate digest
and effective input digest after applying its planning time limit.

Display the selected schedule in Viser:

```bash
uv run --project environments/viz --frozen python examples/task_scheduling.py --output /tmp/task-run --view
```

Open the printed URL, normally `http://127.0.0.1:8080`. The viewer rechecks
the selected plan on CPU and supports shared-time seek, Play, Loop and Reset.
To plan with CUDA, use the [qualified environment](curobo.md):

```bash
uv run --project environments/cuda12 --frozen python examples/task_scheduling.py --backend curobo --output /tmp/task-run-gpu
```

The CUDA environment is separate from the visualization environment. To
view saved files, use the [saved manipulation plan](manipulation.md#view-a-saved-manipulation-plan)
API. CUDA requests never silently switch to CPU planning.

## Define the task catalog

`TaskDomain` is a strict schema-v1 document with format
`kinoweave.manipulation.tasks`. It contains one native scene, movable objects,
initial/goal object modes, a common objective, tasks, and optional task
dependencies. Native robot start/goal states and geometry remain identical
across choices. `kinoweave.io.load`, `dump`, `loads` and `dumps` support this
format. Existing motion-only and manipulation formats are unchanged.

- A `Task` contains named `TaskAlternative` records. Exactly one alternative
  is selected per task; required tasks cannot be skipped.
- Each alternative is a concrete fragment of robot-bound `Skill` records
  with local precedence. A one- or two-arm participant set expresses its
  assignment. Descriptive `parameters` are string pairs for provenance.
- Each skill contains concrete `SkillOption` traces, grasp/object predicates,
  effects and scoped contacts. Selecting an option chooses its supplied
  parameters, such as grasp, IK branch, approach or placement. These values
  and traces must be generated by the caller or an upstream sampler.
- Task-level `ActionOrder` dependencies are whole-fragment barriers: every
  skill in the predecessor must finish before any successor skill starts.
  Within fragments, local precedence keeps its usual skill meaning.

An existing fixed-skeleton manipulation problem can be wrapped in one task
alternative containing its complete skill fragment and precedence. This
preserves object transitions and atomic bimanual handovers.

## Plan and receive improvements

```python
from kinoweave.io import dump, load
from kinoweave.manipulation import (
    RefinementConfig,
    ScheduleConfig,
    SchedulePlanner,
    SkeletonSearchConfig,
    TaskDomain,
)
from kinoweave.roadmap import PRMConfig

domain = load("domain.json", expected=TaskDomain)
planner = SchedulePlanner(
    domain,
    config=ScheduleConfig(time_limit=60, candidate_time_limit=5, max_attempts=64),
    skeleton_config=SkeletonSearchConfig(strategy="input", seed=0),
    prm=PRMConfig(num_samples=128),
    refinement_config=RefinementConfig(time_limit=2, max_iterations=4),
)


def updated(update):
    print(update.attempt, update.elapsed, update.objective.total)
    dump(update.problem, "best-problem.json")
    dump(update.result, "best-result.json")


report = planner.plan(on_improvement=updated)
print(report.status, report.termination_reason)
if report.result is not None:
    dump(report.problem, "problem.json")
    dump(report.result, "result.json")
```

Omit `refinement_config` to compare first feasible plans without refinement.
All alternatives use the same cost weights and `MetricConfig`; callbacks
contain only strict objective improvements with independent CPU evidence.
The first measured feasible plan is also reported. Return `False` to stop
cooperatively, or use `stop_after_first=True`. The live `best_problem`,
`best_result` and `best_objective` remain accessible on the planner.
An objective sample-limit exit can retain a verified first plan with
`objective=None`; it makes no measured cost or quality claim.

`ScheduleReport.status` distinguishes `completed`, `budget_exhausted`,
`cancelled`, `unsupported`, and `invalid_domain`. These describe the search;
check `report.result` separately for a retained successful solution.
`completed/producer_exhausted` with no result means that this finite stream
found no solution. It is not a proof of continuous-space infeasibility.
Individual attempts record invalid or duplicate candidates, fixed-skeleton
timeouts, sampled exhaustion, successes, and optional refinement status.

The total soft deadline covers generation, shared PRM/backend setup, attempts,
refinement, verification and callbacks. `candidate_time_limit` limits each
fixed-skeleton search, capped by the remaining total budget. Native calls,
final CPU verification, and bounded objective measurement cannot be preempted.
A verified incumbent is retained when these operations finish after a deadline.
Named phase timings and `first_verified_seconds` are described in
[scaling and measurement](performance.md#interpret-costs-and-timings).
Iteration, attempt, symbolic expansion, frontier, skill-count, PRM, geometry,
search and metric caps have separate meanings. They do not bound total process
memory or the CUDA allocator.

## Generation, reuse and external producers

`FiniteSkeletonProducer` lazily selects alternatives and skill options, then
enumerates symbolically enabled topological skill orders. It checks declared
object preconditions/effects and requires the goal mode. It namespaces local
skill names as escaped `task/skill` names. Only skills sharing a robot or
referenced object gain resource-order edges, so independent work can overlap.
Different fragments can interleave when dependencies and object states allow.
Commuting linearizations with identical resulting DAGs are deduplicated.

`strategy="input"` follows catalog order. `strategy="distance"` ranks ready
skills by joint-space entry distance, with seeded tie breaking. Neither is
a global assignment optimizer. Limits in `SkeletonSearchConfig` bound
candidate count, expansions, selected skills and pending order states.

The planner builds each base PRM once from the union of all catalog entry/exit
anchors and seeded samples. `plan(graphs=graphs)` instead accepts explicit
native joint graphs. Missing anchors disable the corresponding option.
Skeleton rebinding retains geometry only for identical physical inputs and
settings, allowing only the native wall time limit to differ. Mode-mask
provenance is invalidated on rebinding; static FK caches remain reusable.
Each attempt rebuilds its task/search/conflict state to avoid stale predicates.

A custom `SkeletonProducer` implements `__iter__()` and `feedback(attempt)`.
Yield candidates built with `compile_skeleton(domain, choices, order)`;
`TaskChoice` selects alternative names and every local skill option.
Feedback arrives before the next candidate request, allowing an external
policy to react to geometric failures. Each yielded candidate is recompiled
against the original catalog: tasks, traces, scene, goals and cost cannot be
substituted. Duplicate skeletons are skipped and still receive feedback.
Custom producer/callback calls are synchronous and must cooperate with limits.
Unexpected producer/callback exceptions propagate after cleanup; the live
verified incumbent remains available.

This is finite catalog search. It does not synthesize continuous grasp/IK
parameters, generate new skill traces, implement the paper's full task solver,
or certify optimality. Geometric checks remain sampled. Physical dynamics,
execution and paper benchmark performance are outside this API.
